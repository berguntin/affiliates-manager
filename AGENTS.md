# AGENTS.md

Rules for coding agents working in this repository. Details live in [README.md](README.md), [SPEC.md](SPEC.md) (requirements, risks, decisions §13–14), [docs/arquitectura.md](docs/arquitectura.md) and [docs/creators-api.md](docs/creators-api.md) (Amazon Associates rules). Read the relevant section before changing an area; do not duplicate it here.

## What this is

A private, mobile-first back office (Spanish UI) that finds Amazon.es deals per theme, renders affiliate messages per channel, and publishes them to Telegram (automatic, Bot API) and WhatsApp (assisted, user shares from the phone). One Cloudflare Worker serves the SPA panel, the JSON API, a Telegram webhook ("bot buzón") and two cron tasks. Amazon Associates compliance is a design requirement, not a nice-to-have.

## Stack

- Nuxt 4 (`ssr: false`, SPA) + Nuxt UI 4 + Tailwind 4 in `app/`.
- Nitro with preset `cloudflare_module` on Cloudflare Workers; Cron Triggers bound to Nitro tasks.
- Cloudflare D1 (SQLite) via Drizzle ORM; SQL migrations generated by drizzle-kit, applied by wrangler.
- zod 4 schemas shared by panel and API (`shared/`).
- `@anthropic-ai/sdk` for AI copy; `jose` for Cloudflare Access JWT validation.
- TypeScript strict with `noUncheckedIndexedAccess`; Vitest 4.
- Package manager: **pnpm 10** (`packageManager` in `package.json`). Never use npm/yarn to install or add dependencies; dependency versions are pinned exactly.

## Commands

| Command | Purpose |
|---|---|
| `pnpm install --frozen-lockfile` | Install (runs `nuxt prepare` on postinstall) |
| `pnpm dev` | Local dev server with emulated D1 (needs `.dev.vars`, see README) |
| `pnpm typecheck` | `nuxt typecheck` (app + server) |
| `pnpm test` | Vitest, `tests/**/*.test.ts` |
| `pnpm build` | Worker build into `.output/` |
| `pnpm db:generate` | Generate a migration from `server/db/schema.ts` |
| `pnpm db:migrate:local` | Apply migrations to the local D1 in `.wrangler/` |

CI (`.github/workflows/ci.yml`) runs, in order: `pnpm install --frozen-lockfile`, `pnpm typecheck`, `pnpm test`, `pnpm build`. A change is done only when all four pass.

**Production is owner-only.** Agents never run `pnpm run deploy`, `pnpm db:migrate:remote`, `wrangler deploy`, `wrangler secret put` or any command against the remote D1/Worker. If a change needs one of them (new secret, new migration), say so in the PR description under "Deploy steps".

## Architecture

```
app/        Panel: pages, components, composables (useApi), utils
shared/     Types, zod schemas and pure helpers shared by app and server
server/
  domain/      Pure business logic (deals, dedupe, publication state machine, schedule, messages, intake parsing)
  providers/   ProductProvider port: manual, mock, creators (fase 2); history/ (PriceHistoryProvider, not implemented)
  channels/    ChannelAdapter port: telegram (automatic), whatsapp (assisted); telegram-api.ts is the shared Bot API client
  services/    Orchestration with I/O (D1, fetch, Anthropic): scan, queue, intake, copywriter, templates, runs
  api/         REST endpoints for the panel (file-based routing, `/api/*`)
  routes/      Non-API routes: `webhooks/telegram-intake.post.ts`
  tasks/       Nitro tasks `scan:daily`, `queue:tick`
  middleware/  `auth.ts` (Cloudflare Access JWT on `/api/*`)
  utils/       Auto-imported helpers: useEnv, useDb, readValidated, handleDomainErrors, fetchJsonWithRetry
  db/          `schema.ts` and `migrations/`
tests/      Vitest, mirrors server/ (domain, services, channels, providers, utils)
```

Import rules:
- `server/domain/**` imports only other `server/domain/**` files and `shared/**`. No `db`, `providers`, `channels`, `services`, `utils`, Nitro auto-imports, `fetch`, `useEnv` or `Date.now()`; services pass time and data in. This is how it is today; keep it.
- `shared/**` imports only `shared/**` and `zod`. `app/**` never imports from `server/**`; it talks to the API through `app/composables/useApi.ts`.
- New product sources implement `ProductProvider` (`server/providers/types.ts`); new networks implement `ChannelAdapter` (`server/channels/types.ts`). Do not call Amazon or a network directly from a service or endpoint.

Patterns:
- API handlers validate bodies with `readValidated(event, schema)` using a schema from `shared/schemas.ts`, get params with `requireParam`, and map domain errors with `handleDomainErrors`. Error messages returned to the panel are in Spanish.
- Env/bindings only through `useEnv()` (`server/utils/env.ts`). A new variable is added to `AppEnv`, `.dev.vars.example` and the README env table.
- Outbound HTTP to third parties uses `fetchJsonWithRetry` (`server/utils/http.ts`) or an injectable `fetchFn` parameter so it can be tested without network.
- Dates are epoch ms (`INTEGER`); IDs are UUID `TEXT`; JSON lists are `TEXT` validated with zod. Publishing windows are in `TIMEZONE` (default `Europe/Madrid`); crons are UTC.

## Product rules

- One Amazon tracking ID per channel; links are built in `server/domain/affiliate.ts` and are never rewritten elsewhere.
- Every rendered message ends with the short disclosure line (`ℹ️ Enlace de afiliado · precio sujeto a cambios`, or `ℹ️ Enlace de afiliado` without price). Any shown price carries the date and time it was checked. The renderer adds both outside the editable template (SPEC §14.10); never make them removable.
- No image storage: messages carry the Amazon link and each network builds the preview (SPEC §14.3).
- Candidates expire after 24 h. API-sourced product data (`mock`/`creators_api`) that was not published is purged by `queue:tick` after 24 h (SPEC §14.2); no own price history table.
- Before publishing, the price is refreshed; if it changed, the publication goes to review and is not published.
- Manually typed prices may be published only under the validation mode of SPEC §14.7.
- **Accepted exception (Amazon product page lookup):** `server/services/product-lookup.ts` reads the amazon.es product page (`lookupFromPage`) to prefill title, brand, prices and feature bullets in the manual add flow (panel `POST /api/products/lookup` and bot buzón), only when the Creators API is unavailable. The owner accepts this risk for the validation phase. Limits: only on explicit user action for one ASIN, the result is reviewed by a human before creating a candidate, never used by `scan`, `queue:tick` or any automatic flow, and it must be removed once the Creators API is available. Do not extend it (more fields, more call sites, crawling, retries to bypass blocks).
- AI copy (`server/services/copywriter.ts`, prompts and validators in `server/domain/messages/intro.ts` and `description.ts`): the AI writes only our own text from the theme tone and the user's notes. It never describes or paraphrases Amazon content, never invents numbers, prices, shipping or "historic low" claims, and every output passes the validator before use; on failure the message falls back to the template. Max `MAX_INTROS_PER_RUN` calls per run.
- WhatsApp stays assisted: no unofficial WhatsApp libraries.

## Risk areas

### Amazon compliance and message rendering
`server/domain/messages/**`, `server/domain/affiliate.ts`, `server/domain/deals.ts`, `server/services/templates.ts`, `server/services/product-lookup.ts`, `server/domain/amazon-page.ts`.
- Change only with tests in `tests/domain/messages.test.ts`, `affiliate.test.ts`, `deals.test.ts`, `amazon-page.test.ts`: assert that the disclosure line, the price timestamp and the tracking ID survive every template and format, and that Telegram HTML is escaped.
- Check the relevant rule in `docs/creators-api.md` and SPEC §13–14 before changing behavior; a rule change needs a SPEC §14 entry written by the owner.

### AI copy
`server/services/copywriter.ts`, `server/domain/messages/intro.ts`, `server/domain/messages/description.ts`.
- Any prompt change keeps the validators in place; add cases to `tests/domain/intro.test.ts` / `description.test.ts` / `tests/services/copywriter.test.ts` with outputs that must be rejected.
- Keep the per-run limit and concurrency (each call is a Worker subrequest). Never send secrets or user emails to the model. Model id lives in `COPYWRITER_MODEL`.

### Auth, webhook and secrets
`server/middleware/auth.ts`, `server/utils/access.ts`, `server/routes/webhooks/telegram-intake.post.ts`, `server/services/intake.ts`.
- `/api/*` requires a valid Access JWT and an email in `AUTH_ALLOWED_EMAILS`. `AUTH_DISABLED=true` is honored only under `import.meta.dev`; never widen it.
- The webhook lives outside `/api` and is authenticated with `X-Telegram-Bot-Api-Secret-Token` compared in constant time (`safeEqual`), plus the `INTAKE_ALLOWED_USER_IDS` allowlist. Any new non-`/api` route needs its own authentication.
- Errors and logs contain variable names, never secret values, tokens, JWTs or full emails.
- Test with `tests/utils/access.test.ts`, `tests/domain/intake.test.ts`, `tests/services/intake-links.test.ts`.

### Database and migrations
`server/db/schema.ts`, `server/db/migrations/**`.
- Change the schema in `schema.ts`, then `pnpm db:generate`; commit the generated SQL, the snapshot and `_journal.json` together. Migrations are additive and applied in order on production by the owner.
- Never edit or delete a migration that is on `main`; fix forward with a new one. Hand-written data migrations (like `0005`) go in a new numbered file and must be safe to run once on existing rows.
- Validate with `pnpm db:migrate:local` on a fresh `.wrangler` state plus `pnpm dev`, and with unit tests for any data transformation.

### Queue, scheduling and cron
`server/domain/publication.ts`, `server/domain/schedule.ts`, `shared/queue-cycle.ts`, `server/services/queue.ts`, `server/services/scan.ts`, `server/tasks/**`, `wrangler.jsonc`, `nuxt.config.ts`.
- Cron expressions must match in `wrangler.jsonc` (`triggers.crons`) and `nuxt.config.ts` (`nitro.scheduledTasks`); `tests/domain/queue-cycle.test.ts` enforces the 10-minute tick.
- State changes go through the state machine in `publication.ts` (`tests/domain/publication.test.ts`). Scheduling respects windows, daily limit and `expires_at` (`tests/domain/schedule.test.ts`).
- A failure in one theme or publication must not abort the run; it is recorded in `runs` / `publications.error`.
- Worker limits: keep external calls per invocation bounded (`SEARCH_LIMIT` per theme in `server/services/scan.ts`, `MAX_INTROS_PER_RUN` for AI).

## Privacy and security

- Personal data handled: allowed panel emails (`AUTH_ALLOWED_EMAILS`, `event.context.userEmail`) and Telegram user/chat IDs in `intake_drafts`. Do not log them, return them to other users, or send them to third parties.
- Secrets exist only as Wrangler secrets in production and in `.dev.vars` locally. Never commit them, print them, or put them in `wrangler.jsonc` `vars`.
- `preview_urls` stays `false` in `wrangler.jsonc` (Access does not protect preview URLs).

## Code rules

- TypeScript strict; no `any`, no `@ts-ignore`/`@ts-expect-error` without a comment explaining why. Validate external input (request bodies, Telegram updates, provider responses) with zod or explicit checks.
- Business logic goes in `server/domain` with Vitest tests; new domain behavior ships with tests. Tests use fixtures (`tests/domain/fixtures.ts`) and injected `fetchFn`, never real network.
- Language: UI text, API error messages, commit messages and docs in Spanish (Spain). Identifiers in English. **New code comments in English**; do not rewrite existing Spanish comments just to translate them.
- Panel is mobile-first: check new screens at phone width; use Nuxt UI components; icons from `@iconify-json/lucide` (`i-lucide-*`), bundled (no runtime Iconify calls). Give icon-only buttons an accessible label.
- Follow existing formatting (2 spaces, single quotes, no semicolons). There is no linter or formatter configured.

## Workflow

- Every task starts from an up-to-date local `main`, always with exactly these steps:
  ```bash
  git switch main
  git pull --ff-only           # fetch + fast-forward local main to origin/main
  git switch -c <branch-name>  # branch from local main
  ```
  Do not create the branch from `origin/main` (`git switch -c <branch> origin/main` makes the new branch track `main`, and a later `git push` fails or targets the wrong branch). If `git pull --ff-only` fails because local `main` has diverged, stop and ask the owner. The first push sets the branch's own upstream: `git push -u origin <branch-name>`.
- If `main` moves, merge it into your branch before opening or updating the PR (no rebase/force push on shared branches without the owner's OK).
- Changes reach `main` only through a pull request; never commit or push directly to `main`. One branch per task, named `<type>/<short-kebab-desc>` (e.g. `feat/extraccion-precios-amazon`).
- Commits follow the repo style: Conventional Commits with a Spanish scope and summary, e.g. `feat(buzón): …`, `fix(cola): …`, `docs: …`.
- PR description: what changed, how it was validated, and "Deploy steps" if a secret or migration is needed.

## Do not touch

- `.env`, `.dev.vars`, `.wrangler/`, `.nuxt/`, `.output/`, `node_modules/` (local, ignored).
- `server/db/migrations/*` already on `main` and `server/db/migrations/meta/*` except via `pnpm db:generate`.
- `pnpm-lock.yaml` except via pnpm.
- The D1 `database_id` in `wrangler.jsonc`.
- New env variable: add it to `AppEnv` (`server/utils/env.ts`), `.dev.vars.example` (commented, fake value) and the README env table; never add a real value anywhere in the repo.

## Known current state

Debt where the code or docs do not yet match these rules. Do not assume these are fixed; do not copy these patterns.

- The Amazon product page lookup (accepted exception above) is not yet recorded in SPEC §14, and SPEC §14.8, §14.9, README ("sin scraping") and `docs/arquitectura.md` §10 still say Amazon pages are never fetched. It sends a browser `User-Agent` instead of identifying itself as the intake resolver does (`INTAKE_USER_AGENT`).
- Product data read from the Amazon page (title, prices, features) is stored in `intake_drafts` and in manual deals, which `queue:tick` never purges (the 24 h purge only covers `mock`/`creators_api` deals). `intake_drafts` rows, including Telegram user/chat IDs, are never deleted.
- Feature bullets read from the Amazon page are inserted verbatim into the "texto propio" (`withFeatureBullets` in `server/services/intake.ts`, `featureBullets` in `server/domain/amazon-page.ts`), which SPEC §14.9 says must not contain Amazon content.
- `resolveShortLink` (`server/services/intake.ts`) follows up to 4 redirect hops to any non-Amazon host.
- `docs/arquitectura.md` mentions `NUXT_AUTH_DISABLED` (the code reads `AUTH_DISABLED`), "repositorios" in `server/db/` (there are none; queries live in services), `fetchWithRetry` (the helper is `fetchJsonWithRetry`) and says tests cover only `server/domain`.
- The README env table omits `INTAKE_BOT_TOKEN`, `INTAKE_WEBHOOK_SECRET`, `INTAKE_ALLOWED_USER_IDS` and `TELEGRAM_API_BASE` (they are in `AppEnv` and, except the last, in `.dev.vars.example`). `ANTHROPIC_API_KEY` is missing from `.dev.vars.example`.
- `package.json` scripts `preview` and `deploy` call `npm run build`; it works but is inconsistent with pnpm.
- Most history was committed directly to `main`; the PR-only rule applies from now on. A stale `origin/master` branch exists; the default branch is `main`.
- No linter or formatter is configured.
